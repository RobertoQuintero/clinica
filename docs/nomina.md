# Nómina (payroll)

- Module under `app/dashboard/nomina/`. It has **Periodos** (`nomina/periodos/`, spec 52), **Procesar nómina** (`nomina/procesar/`, spec 53) the per-employee **Detalle** (`nomina/procesar/[id_empleado]/`, spec 54) **Comisiones** (`nomina/comisiones/`, spec 56) **Horas extra** (`nomina/horas-extra/`, spec 60 detection and authorization, spec 61 payment) **Faltas** (`nomina/faltas/`, spec 62) and **Retardos** (`nomina/retardos/`, spec 63); `nomina/page.tsx` redirects to Periodos. Five concepts are calculated: the base salary, the commission for attended consultas (spec 56), the commission for paid onychomycosis treatments (spec 57), the commission for sold products (spec 58) and the authorized overtime (spec 61); the three commissions and the overtime are operativa only. The base salary is reduced by the unjustified absences of podólogos (spec 62) and by their unjustified lateness (spec 63, half a day per severe delay plus configurable accumulation tiers per payroll frequency) in both payrolls. Other bonuses, punctuality/attendance bonuses, deductions (IMSS/ISR), approval/payment, receipts, dispersion and CFDI stamping are not built.
- Lives in the `payroll` schema (separate from `RH`, like `BILLING`). Besides `payroll.periods`, `payroll.period_employees`, `payroll.commission_tiers` and the spec 57 tables (`treatment_commission_settings`, `treatment_commission_settings_log`, `period_employee_treatments`), the spec 58 table (`period_employee_product_sales`), the spec 60 tables (`overtime_settings`, `overtime_settings_log`, `overtime_authorizations`), the spec 61 table (`period_employee_overtime`), the spec 62 tables (`absence_justifications`, `period_employee_absences`), the spec 63 tables (`lateness_settings`, `lateness_tiers`, `lateness_settings_log`, `lateness_justifications`, `period_employee_lateness`), the schema holds catalogs not yet consumed: `cat_taxed_exempt`, `perceptions`, `tablas_retencion` (keyed by `id_payment_period` + `ejercicio`).

## Access

- Only `id_role` 1 and 4 (`PAYROLL_ALLOWED_ROLE_IDS` in `lib/payroll/constants.ts`).
- Gated in three places: `proxy.ts` (anything under `/dashboard/nomina` -> `/dashboard`), `navConfig.tsx` (`excludeRoles: [2, 3, 5, 6]`, the complement of the constant) and `assertPayrollAccess()` in `lib/payroll/access.ts` (server-only; every action in `periodos/actions.ts` and `procesar/actions.ts` returns `{ ok: false }` for other roles). `access.ts` also holds `ActionResult`, `IPayrollSession` and `PERIOD_ROW_SELECT`; it is not a `"use server"` file so none of it is exposed as a public action.
- The active branch comes from the `sel_sucursal` cookie with JWT fallback, never from client input. Each period belongs to a single branch.

## `payroll.periods`

- One row per period per branch: `id_sucursal`, `id_payment_period` (FK to `RH.payment_periods`, the SAT `c_PeriodicidadPago` catalog), `codigo`, `ejercicio`, `consecutivo`, four `date` columns (`fecha_inicio`, `fecha_fin`, `fecha_corte`, `fecha_pago`), `status`, and audit (`created_by`, `created_at`, `updated_at`).
- DDL is in `queries.txt` (block `NOMINA PAYROLL`). `CK_periods_fechas` enforces `inicio <= corte <= fin` and `pago >= corte`; `CK_periods_status` restricts `status` to 1..4.
- Types: `interfaces/payroll_period.ts`. All dates are plain strings (see the date/time rules in `CLAUDE.md`); SELECTs use `CONVERT(varchar(10|19), ..., 120)`.

## Frequencies

Only SAT keys with a code letter and a date rule are offered (`PAYROLL_FREQUENCY_LETTER_BY_SAT_KEY`): 01 D, 02 S, 03 C, 04 Q, 05 M, 06 B, 10 X. Keys 07, 08, 09 and 99 are never offered. A frequency must also be active (`status = 1`) in `RH.payment_periods`. The frequency cannot be changed after creation.

## Period code

`NOM-{ejercicio}-{letter}{consecutivo, min. 2 digits}`, e.g. `NOM-2026-S38`.

- `ejercicio` is the year of `fecha_inicio`; a period crossing New Year counts in the year it starts.
- `consecutivo` is `MAX + 1` per branch + ejercicio + frequency, computed inside the create batch.
- The code is generated on the server, read-only, and never regenerated on edit.
- **Gaps are expected and the consecutivo is never reused**: deleting S05 means the next one is S07 if S06 already exists. The code is an identifier, not a fiscal folio.

## Suggested dates (`lib/payroll/periodDates.ts`)

`suggestPeriodDates(satKey, previousEndDate, today)` works on `"YYYY-MM-DD"` strings only.

- **Start:** day after the last period's end for that frequency in the branch. With no previous period: Monday of the current week (weekly), day 1 or 16 (biweekly), day 1 (monthly), today otherwise.
- **End:** weekly = start + 6; biweekly = day 15 or last day of month; monthly = last day of month; others = start + fixed length (01: 1, 03: 14, 06: 60, 10: 10).
- **Payment:** last Friday <= end. **Cutoff:** payment - 2 days (Wednesday), never before the start.
- Periods shorter than 7 days: payment = end and cutoff = end.
- The four dates are always editable; the suggestion is only a starting point.

## Validation and concurrency

- `lib/payroll/schemas.ts` (zod) validates date format, real calendar dates and order. Errors return as `ActionResult` and show in the modal.
- Overlap is rejected between periods of the **same frequency in the same branch**; different frequencies may overlap.
- `createPayrollPeriod` and `updatePayrollPeriod` run one SQL batch with `BEGIN TRAN` and `UPDLOCK, HOLDLOCK` (`db` does the check and write together; the explicit transaction is what keeps the locks held). `UQ_periods_consecutivo` is the last barrier; a race surfaces as "Intenta de nuevo", never a 500.

## Status

`status`: 1 Programada, 2 En cálculo, 3 Aprobada, 4 Pagada (`PAYROLL_PERIOD_STATUS`). Periods are created as 1. Today the only transitions are 1 -> 2 (calculate) and 2 <-> 2 / 2 -> 1 (recalculate / revert), see "Salary calculation". Approved (3) and Paid (4) are not reachable yet.

- **Edit** changes only the four dates and `updated_at`, and only while `status = 1`.
- **Delete** is a physical `DELETE`, only while `status = 1`.
- Both re-check `id_sucursal` and `status = 1` inside the statement itself, so a stale UI cannot change a period that already moved on. While a period is 2 (En cálculo) it can be neither edited nor deleted; revert it to 1 first.

## Salary calculation (spec 53)

Screen `/dashboard/nomina/procesar`; actions in `nomina/procesar/actions.ts`.

- **Table `payroll.period_employees`** (DDL in `queries.txt`): one snapshot row per period + employee + type (`tipo_nomina`: `'O'` operativa, `'F'` fiscal), with `salario_diario` used, `dias` (net paid days since spec 62), `dias_falta`, `importe_salario`, `calculated_by`, `calculated_at`. `UQ_period_employees` prevents duplicates and doubles as the index by `id_period`. The FK to `payroll.periods` has no cascade: a period can only be deleted at status 1, where it has no snapshot.
- **Who is included** (evaluated at calculation time): `RH.empleados` with `status = 1`, `activo = 1`, `id_sucursal` = the period's branch, `id_periodo_pago` = the period's `id_payment_period` and `fecha_ingreso <= fecha_fin`. **An employee without `id_periodo_pago` never enters payroll**, not even the excluded notice: capture the frequency in the employee record first.
- **Days:** `fecha_fin - max(fecha_inicio, fecha_ingreso) + 1` calendar days, **minus `dias_falta`** (unjustified absences of controlled employees, spec 62; see "Faltas (spec 62)"). `dias` stores the net days, so calendar days are `dias + dias_falta`. Lateness does not change `dias`: it is discounted through `dias_retardo` (spec 63; see "Retardos (spec 63)"). No `fecha_baja` exists, so inactive employees are simply not included.
- **Amount:** `ROUND(salary * (dias - dias_retardo), 2)` per employee (`dias_retardo` is 0 without lateness, so snapshots from before spec 63 keep their amount). Operativa uses `salario_diario`, fiscal uses `salario_diario_fiscal`; there is **no fallback** between them. An employee only enters a type when its salary is `> 0`, so they can be in one and not the other. Screen totals add the already-rounded amounts.
- **Snapshot:** it stores the salary used, so editing the employee record afterwards does not change a saved result until the period is recalculated.
- **Transitions** (each one is a single SQL batch with `BEGIN TRAN` and the period read `WITH (UPDLOCK, HOLDLOCK)`, checking branch and status inside the batch):
  - `calculatePayrollPeriod`: status 1 or 2 -> deletes the period's snapshot, inserts the `'O'` and `'F'` rows and leaves the period at 2. Used for both "Calcular" (1) and "Recalcular" (2).
  - `revertPayrollCalculation`: status 2 -> deletes the snapshot and returns the period to 1 so its dates can be edited again.
- **The calculation lives in SQL** (`INSERT ... SELECT`); `lib/payroll/salaryCalculation.ts` (`countPaidDays`, `calculateSalaryAmount`) restates the rule as pure string-based functions. If they diverge, the SQL is the source of truth.
- **Read side:** `getPayrollProcessPage(filters)` resolves the period (requested id in the active branch; otherwise the one whose range includes today; otherwise the most recent), returns the snapshot rows with puesto/search filters, unfiltered totals, puesto options and the "excluded" employees (eligible by branch and frequency but without the salary of the selected type, computed on the fly).

## Comisión por consultas (spec 56)

Screen `/dashboard/nomina/comisiones` (Server Component; client leaves are `CommissionTierModal` and `DeleteCommissionTierButton`); actions in `nomina/comisiones/actions.ts` (`getCommissionTiers`, `createCommissionTier`, `updateCommissionTier`, `deleteCommissionTier`), all behind `assertPayrollAccess()` and scoped to the session's `id_empresa` (`IPayrollSession` carries it).

- **Catalog `payroll.commission_tiers`** (DDL and seed in `queries.txt`): per company, `min_consultas`, `max_consultas` (`NULL` = open tier), `importe` (fixed amount for the whole tier, not per consulta). Seed: 1-10 -> $100, 11-25 -> $200, 26-35 -> $300, 36+ -> $500. Physical delete. The catalog is **live**: editing it never changes a saved snapshot until the period is recalculated.
- **Tier rules**, validated with `zod` (`commissionTierSchema`) and again in SQL inside the same transaction that writes (`BEGIN TRAN` + `UPDLOCK, HOLDLOCK` over the company's tiers): `min >= 1`, `max >= min` or null, `importe >= 0`, **no overlapping ranges** and **at most one open tier**. **Gaps are allowed** (a count that falls in a gap earns $0). The modal warns about overlaps with `tierRangeOverlaps` before submitting; the server is the authority.
- **Which consultas count** for an employee: `consultas.id_podologo` is one of the `users.id_user` linked to the employee (`users.id_empleado`, spec 55), with `deleted_at IS NULL`, **not cancelled**, `fecha_fin IS NOT NULL` and `fecha` inside the period (`>= fecha_inicio` and `< fecha_fin + 1 day`, because `fecha` is a `datetime`). `cancelada` is a **nullable** bit and `NULL` means "not cancelled" (the app reads it that way; ~98% of rows are `NULL`), so the SQL uses `ISNULL(c.[cancelada], 0) = 0`; a plain `= 0` would count nothing.
- **No branch filter** (every consulta of the user counts wherever it happened) and **no user `status` filter** (consultas by a user deactivated later still count).
- **One tier per employee:** the counts of all their linked users are summed and a single tier is applied to the total. The tier pays its full `importe`; 0 consultas, a gap or an empty catalog give $0. Not prorated for someone who joined mid-period.
- **Only operativa (`'O'`)** commissions. `'F'` rows are inserted with `consultas_atendidas = 0` and `importe_comision = 0`. An employee without operativa salary (`> 0`) does not enter payroll, so they earn no commission.
- **Snapshot:** `payroll.period_employees` gains `consultas_atendidas` and `importe_comision` (spec 57 adds three more columns, see below), filled by the same `INSERT ... SELECT` of `calculatePayrollPeriod` through two `OUTER APPLY` (count, then `TOP 1` tier ordered by `min_consultas DESC`). Snapshots calculated before this spec stay at 0 / 0 until recalculated. `lib/payroll/commissionTiers.ts` (`findCommissionTier`, `calculateCommissionAmount`, `formatTierRange`) restates the tier rule in TS; **if they diverge, the SQL is the source of truth**.
- **Screens:** Procesar shows "Com. consultas" (with the consulta count) and "Total percepciones" (sueldo + both commissions since spec 57, computed in the SELECT); the summary card and the footer total are sums over the whole type, ignoring puesto/search filters. The detail adds the `comision_consultas` line (omitted when the amount is 0). Its description shows the count plus the tier range only when the *current* catalog tier for that count still pays the snapshot's amount; otherwise just the count.
- **Out of scope:** tiers per branch/role, effective dates, a list of counted consultas, fiscal commission, manual adjustment, recomputing only the commission.

## Comisión por tratamientos de onicomicosis (spec 57)

Pays each employee a fixed amount per onychomycosis treatment that their linked users registered and that was **settled** inside the period. Rules of origin: `references/docs/tratamiento_onicomicosis.md`. Configuration lives on `/dashboard/nomina/comisiones` (below the tiers table); the calculation is in `calculatePayrollPeriod`.

- **Settlement rule.** A treatment is settled on the `created_at` of the partial payment (`Tratamiento_onicomicosis_pagos.id_tratamiento_pago_tipo = 2`, `status = 1`) at which the running sum of those payments, ordered by `created_at` then `id_tratamiento_pago`, reaches `umbral_liquidacion` (`>=`, seed $5,000). Type 1 (advance) payments and `status = 0` payments never count. The period is decided by that settlement date, not by the treatment's `created_at`, so a treatment created earlier but finished inside the period counts in it.
- **Attribution.** `Tratamiento_onicomicosis.id_usuario` -> `users.id_empleado` (spec 55). Not `id_especialista` (external doctor, already paid through `egresos`) and not the consulta's `id_podologo`. An employee's linked users are summed. No branch filter and no user `status` filter, same as spec 56.
- **What counts.** `ISNULL(id_stage, 0) <> 6` (not cancelled) evaluated at calculation time; settlement date inside `[fecha_inicio, fecha_fin + 1 day)`; not already present in `payroll.period_employee_treatments`.
- **Amount.** `tratamientos_onicomicosis x importe_por_tratamiento` (seed $500), no proration or cap. Only operativa (`'O'`): `'F'` rows stay at 0 / 0 / 0 and get no breakdown.
- **Configuration and change log.** `payroll.treatment_commission_settings` has one row per company (PK `id_empresa`) with `importe_por_tratamiento` (0 allowed: it switches the commission off) and `umbral_liquidacion` (> 0), plus `updated_by` / `updated_at`. Without a row nobody earns this commission. `payroll.treatment_commission_settings_log` receives one row per save that changes a value (previous and new values of both fields, `NULL` previous when there was no row); a save with no change writes nothing. `updateTreatmentCommissionSettings` validates with `zod` (`treatmentCommissionSettingsSchema`) and compares, writes and logs in one transaction (`UPDLOCK, HOLDLOCK`). The seed does not write to the log. Actions: `getTreatmentCommissionSettings`, `getTreatmentCommissionSettingsLog` (last 20) and `updateTreatmentCommissionSettings`, in `nomina/comisiones/actions.ts`. Only `TreatmentCommissionSettingsModal` is a client component; the card and the log are Server Components.
- **Pay-once lock.** `payroll.period_employee_treatments` has one row per paid treatment (`id_period_employee`, `id_tratamiento`, `fecha_liquidacion`, `total_parciales`) with `UNIQUE (id_tratamiento)`: **a treatment is paid once in the whole history**, whatever the period, frequency or branch. Deleting and re-capturing a payment, or two overlapping periods, cannot pay it twice. The FK to `period_employees` is `ON DELETE CASCADE`, so "Recalcular" and "Revertir" free the period's treatments with the `DELETE` they already run. There is no FK to `dbo.Tratamiento_onicomicosis` on purpose. Two simultaneous calculations competing for the same treatment end with one success and one "Otro cálculo tomó alguno de estos tratamientos al mismo tiempo. Intenta de nuevo." (`UQ_period_employee_treatments_tratamiento` in `describePayrollCalculationError`).
- **Calculation order** inside the calculate batch: delete the period's snapshot (cascade frees its treatments) -> build the temp table `#liquidated` (cumulative sum `SUM() OVER`, first payment reaching the threshold, filters above) -> `INSERT` the snapshot with three new columns (`tratamientos_onicomicosis`, `importe_por_tratamiento` frozen, `importe_comision_tratamientos`) counting `#liquidated` per employee -> `INSERT` the breakdown from `#liquidated` joined to the new `'O'` snapshot rows. The count and the breakdown come from the same set, so they cannot differ. `lib/payroll/treatmentCommission.ts` (`findLiquidationPayment`, `calculateTreatmentCommissionAmount`, `describeTreatmentCommission`) restates the rule in TS (cents-based sum, string date comparison); **if they diverge, the SQL is the source of truth**.
- **Consequences.**
  - A treatment registered by someone who is not in that period's operativa payroll (e.g. no operativa salary) is not paid and not marked as paid; since its settlement date will not fall in a later period, in practice it never commissions. Fix the employee and recalculate that same period.
  - If the threshold changes, the settlement date of not-yet-paid treatments is recomputed with the new value on the next calculation; a treatment that moves into an already calculated period needs that period recalculated.
  - **No retroactive discount:** cancelling a treatment or deleting its payments after a period paid it does not change that period; only recalculating that same period excludes it.
  - Snapshots calculated before this spec stay at 0 / 0 / 0 (column defaults) and show as before until recalculated, provided another period has not taken their treatments.
- **Screens.** Procesar: "Com. consultas" and "Com. onicomicosis" (with the treatment count as secondary text); "Total percepciones", the summary card and the footer add sueldo + both commissions. Detail: `buildPerceptionLines` adds `comision_tratamientos` ("N tratamientos x $X" from the frozen unit amount, omitted when the amount is 0) and `PayrollPaidTreatmentsList` (Server Component) lists patient, settlement date and a link to `/dashboard/tratamientos/[id]`; `paidTreatments` is `[]` for fiscal.
- **Out of scope:** reversing a paid commission, commission for the specialist or the consulta's podólogo, fiscal payroll, amounts per branch/role/treatment type, effective dates, counting type 1 payments toward the threshold, manual adjustment, releasing a paid treatment by hand, recomputing only the commission, pure-commission employees, a global report of paid/pending treatments.

## Comisión por venta de productos (spec 58)

Pays each employee the `bono_venta` of every piece their linked users sold inside the period, in consultas or in direct sales. Each line pays `cantidad x bono_venta`. Rules of origin: `references/docs/comision_ventas.md`; this implementation differs in one point: for consultas the period is decided by `consultas.fecha`, not `consultas.created_at`, to match spec 56. The calculation is in `calculatePayrollPeriod`.

- **Sources and attribution.**
  - Consultas: `consulta_productos`, attributed to the consulta's `id_podologo`.
  - Direct sales: `VentasDetalle`, attributed to `Ventas.id_usuario`, i.e. **whoever captured the sale**. A shared cashier account linked to an employee would give that employee every sale made with it; check the user-employee links (spec 55) before calculating.
  - Both go through `users.id_empleado`. An employee's linked users are summed. No branch filter and no user `status` filter, same as specs 56 and 57.
- **What counts.**
  - Consulta line: `consulta_productos.status = 1`, the consulta has `deleted_at IS NULL` and `ISNULL(cancelada, 0) = 0`, and `consultas.fecha` is inside `[fecha_inicio, fecha_fin + 1 day)`. `fecha_fin IS NOT NULL` is **not** required (the product was sold and stock was already discounted even if the consulta was not closed; spec 56 requires it because it counts *attended* consultas).
  - Direct sale line: `Ventas.status = 1` and `Ventas.created_at` inside the same half-open range.
  - Both: the product has `bono_venta > 0` (lines with `NULL` or 0 bonus are neither in the breakdown nor locked, so capturing the bonus later and recalculating pays them), the line is not already in `payroll.period_employee_product_sales`, and `Products.status` is ignored (a product deactivated after being sold still pays).
- **Amount.** `ROUND(cantidad x bono_venta, 2)` **per line**, then summed per employee, so the grouped list in the detail adds up to the cent with the snapshot. The bonus is the one current in `inventory.Products` at calculation time and is frozen in the breakdown. For `split = 1` products `cantidad` is in pieces, so the bonus is paid per piece. Only operativa (`'O'`): `'F'` rows stay at 0 / 0 and get no breakdown.
- **Snapshot.** `payroll.period_employees` gains `piezas_vendidas` (`SUM(cantidad)`) and `importe_comision_productos`, both `NOT NULL DEFAULT 0` with a `CHECK >= 0`. Snapshots calculated before this spec stay at 0 / 0 until recalculated.
- **Pay-once lock.** `payroll.period_employee_product_sales` has one row per paid line (`id_period_employee`, `origen` `'C'` consulta / `'V'` direct sale, `id_linea_origen`, `id_documento_origen`, `id_producto`, `fecha_venta`, `cantidad`, frozen `bono_venta`, `importe_comision`) with `UNIQUE (origen, id_linea_origen)`: **a line is paid once in the whole history**, whatever the period, frequency or branch. Two columns (`origen` + `id_linea_origen`) instead of two nullable ones because a filtered unique index would need specific `SET` options on every inserting connection. The FK to `period_employees` is `ON DELETE CASCADE`, so "Recalcular" and "Revertir" free the period's lines with the `DELETE` they already run (`revertPayrollCalculation` is unchanged). There is no FK to `consulta_productos`, `VentasDetalle` or `Products` on purpose: `deleteConsultaProducto` does a physical `DELETE` and the paid breakdown must survive it. Two simultaneous calculations competing for the same line end with one success and one "Otro cálculo tomó algunas de estas ventas al mismo tiempo. Intenta de nuevo." (`UQ_period_employee_product_sales_linea` in `describePayrollCalculationError`).
- **Calculation order** inside the calculate batch, after `#liquidated` (spec 57): build `#product_sales` (consulta lines `UNION ALL` direct sale lines, with the filters above) -> `INSERT` the snapshot with the two new columns from an `OUTER APPLY` over `#product_sales` (only when `tipo_nomina = 'O'`) -> `INSERT` the breakdown from `#product_sales` joined to the new `'O'` snapshot rows. The snapshot and the breakdown come from the same set, so they cannot differ. `lib/payroll/productSalesCommission.ts` (`calculateProductSaleLineCommission`, `describeProductSalesCommission`) restates the rule in TS; **if they diverge, the SQL is the source of truth** (the amount that is paid and shown is always the one SQL stored).
- **Consequences.**
  - Someone who sold but is not in that period's operativa payroll (e.g. no operativa salary) does not get the line, and the line is not marked as paid; since its date will not fall in a later period, in practice it never commissions.
  - If `bono_venta` changes, lines already paid keep the frozen bonus; recalculating a period uses the bonus current at that moment.
  - The same consulta can yield both the consultas commission (spec 56) and a product commission in the same period, because both use `consultas.fecha`.
  - **No retroactive discount:** cancelling a sale or a consulta, deactivating the line or changing its quantity after a period paid it does not change that period; only recalculating that same period picks up the change.
- **Screens.** Procesar: "Com. Ventas" column (amount plus "N piezas" as secondary text); "Total percepciones", the summary card and the footer add sueldo + the three commissions. Detail: `buildPerceptionLines` adds `comision_productos` ("Comisión por venta de productos", "N piezas vendidas", omitted when the amount is 0) and `PayrollSoldProductsList` (Server Component, no links) lists the paid lines **grouped by product and frozen bonus** (`GROUP BY id_producto, p.name, bono_venta`, ordered by commission descending then name) with a total row; `soldProducts` is `[]` for fiscal or without paid lines and the list is then hidden.
- **Out of scope:** reversing a paid commission, fiscal payroll (and its SAT key / `payroll.perceptions`), historical bonus or bonus validity dates, bonus per branch/role or as a percentage of price, attributing a consulta's sale to whoever added the product, a line-by-line view with links, a global report of paid/pending lines, editing the bonus from payroll (it is edited in the product catalog, spec 37), manual adjustment, releasing a paid line by hand, recomputing only this commission.
- **Known risks.** Old `consulta_productos` rows from before spec 17 store a legacy `dbo.productos` id in `id_producto`; do not create periods with dates before that migration. `#product_sales` scans `consultas` and `Ventas` by date; if the calculation gets slow, add indexes on `consultas([fecha])` and `Ventas([created_at])` without changing the logic.

## Horas extra (spec 60)

Detects overtime per employee and day from the checadas, and lets an admin authorize (adjusting the hours), reject or leave each day pending. Rules of origin: `references/docs/horas_extras.md`. Payment arrived with spec 61 (see "Horas extra: pago (spec 61)" below); the screen's fixed notice now reads "Las horas autorizadas se pagan al calcular la nómina del periodo."

- **Screen and actions.** `/dashboard/nomina/horas-extra` (`nomina/horas-extra/`), state in the URL (`periodo`, `estado=pendiente|autorizada|rechazada`, `q`, `pagina`; 25 rows per page). `actions.ts` exposes `getOvertimePage`, `getOvertimeSettings`, `getOvertimeSettingsLog`, `updateOvertimeSettings`, `decideOvertimeDay` and `clearOvertimeDecision`, all behind `assertPayrollAccess()` with the branch from the session and `zod` schemas in `lib/payroll/schemas.ts`. Types: `interfaces/payroll_overtime.ts`.
- **Who is reviewed.** The employees eligible for the operativa payroll of the period (spec 53 rules, `ELIGIBLE_OPERATIVE_EMPLOYEE_CONDITIONS` in `lib/payroll/eligibleEmployees.ts`): `status = 1`, `activo = 1`, the period's branch and frequency, `salario_diario > 0` and `fecha_ingreso <= fecha_fin`. Only the days from `max(fecha_inicio, fecha_ingreso)` to `fecha_fin` are reviewed. Since spec 61 `lib/payroll/eligibleEmployees.ts` also exports `ELIGIBLE_EMPLOYEE_BASE_CONDITIONS` (the same conditions without the salary one), and `ELIGIBLE_OPERATIVE_EMPLOYEE_CONDITIONS` is that base plus `e.salario_diario > 0`; `calculatePayrollPeriod` uses the base plus the salary of each type, so there is a single copy of the rule. `resolvePeriod` (period from the URL, the current one, or the most recent) lives in `lib/payroll/period.ts`, shared with Procesar.
- **Detection** (`lib/payroll/overtimeDetection.ts`, pure, no DB, no `Date` over raw strings):
  - Checadas are grouped by the date of `fecha_hora`; the first `entrada` and the last `salida` of the day are used, so lunch in between does not count. A day is **incomplete** with the same criterion as the employee attendance tab (`summarizeAttendanceEvents`): it detects 0 h but is listed as "Checada incompleta".
  - Scheduled day (`RH.empleado_horarios`, spec 59): extra = `max(0, hora_entrada_1 - first entrada)` + `max(0, last salida - end of the last block)`, where the last block ends at `hora_salida_2` if it exists, else `hora_salida_1`. A late arrival is **not** deducted.
  - Rest day (no schedule row for that weekday): every worked hour is extra.
  - The day total is rounded **down** to 30-minute blocks (2 h 17 min -> 2.0 h), with no minimum.
  - An employee with no schedule rows at all never detects anything; the screen lists them in a "Sin horario definido" notice linking to their Horario tab.
  - The **current** schedule is used for the whole period (no schedule history), so changing an employee's schedule recomputes the detection of past days.
  - Weekday of a `"YYYY-MM-DD"` comes from `Date.UTC(...)` over its numeric parts; times are subtracted as integer minutes from `"HH:mm"`.
- **Tables** (schema `payroll`, DDL in `queries.txt`, block `NOMINA PAYROLL`):
  - `overtime_settings`: one row per company with `limite_horas_dobles_periodo` (seed 9) and `tope_horas_dia` (seed 16). The limit is consumed by spec 61 (hours above it are paid triple).
  - `overtime_settings_log`: change log, same pattern as `treatment_commission_settings_log`; a save with no changes writes nothing.
  - `overtime_authorizations`: one row per employee and date (`UNIQUE (id_empleado, fecha)`) with `estado` (`'A'` authorized / `'R'` rejected), `horas_autorizadas`, `horas_detectadas` at decision time, an optional comment and who/when decided. **No row = "Pendiente"**, and "Volver a pendiente" deletes the row. Deciding again overwrites the row (no decision history).
  - `CK_overtime_authorizations_estado` needs `[horas_autorizadas] IS NOT NULL` in the `'A'` branch: without it SQL Server accepts `'A'` with `NULL` hours, because `NULL > 0` is UNKNOWN and a `CHECK` lets UNKNOWN pass.
- **The decision belongs to the employee's day, not to the period.** There is no `id_period` column or FK to `payroll.periods`, so a decision survives if a period is deleted and created again; spec 61 finds it by date range. `id_period` travels in the writes only to validate inside the transaction that the period belongs to the active branch and is in status 1 or 2, that `fecha` is inside its range and that the employee is eligible that day (also `fecha_ingreso <= fecha`).
- **Decisions** (`decideOvertimeDay`): authorized hours must be a multiple of 0.5, greater than 0 and at most `tope_horas_dia` (read in the same transaction; the cap is not a `CHECK` because it changes, and lowering it does not change saved authorizations). Authorized hours may exceed the detected ones, which is how missing checadas are covered. `horas_detectadas` is **always recomputed on the server** (client values are dropped by the schema). Rejecting stores `NULL` hours. With the period in status 3 or 4 the list is read-only and both actions return `{ ok: false }`.
- **List.** A day is listed if it has detected overtime, is incomplete, or already has a saved decision (even if today's detection is 0). If the detection today differs from `horas_detectadas` at decision time, the row shows "Detectado cambió: X -> Y" and keeps its `horas_autorizadas`. The summary cards (pending days, detected hours, authorized hours) cover the whole period and do not change with the filters. `getOvertimePage` runs four SELECTs (employees, schedules, checadas, decisions), detects in TypeScript, then filters and paginates.
- **Components** (`horas-extra/componentes/`): Server Components `OvertimeDaysTable`, `OvertimeSummaryCards`, `EmployeesWithoutScheduleNotice`, `OvertimeSettingsCard`, `OvertimeSettingsLog` (a `<details>`); client components only `OvertimeToolbar`, `OvertimeSettingsModal` and `OvertimeDecisionModal`. `OvertimeDecisionModal` renders through a portal to `document.body` because its button sits in a table cell with `text-right`, which the dialog would otherwise inherit.
- **Out of scope (spec 62 and later):** fiscal payroll and ISR, tolerances and attendance discounts, prima dominical and holidays, shifts crossing midnight, schedule history, "authorize all" in bulk and adding days that are not listed.
- **Known risks.** A checador that sends a wrong `tipo` produces incomplete days in bulk (they are listed, not lost). A shift that ends after midnight leaves one incomplete day and a stray `salida`.

## Horas extra: pago (spec 61)

`calculatePayrollPeriod` pays the overtime authorized in spec 60. Rules of origin: `references/docs/horas_extras.md`. Operativa only: the `'F'` rows keep the five overtime columns at 0 and have no breakdown.

- **What is paid.** Only `overtime_authorizations` rows with `estado = 'A'` whose `fecha` is inside the period, on or after the employee's `fecha_ingreso`, for employees eligible to the operativa payroll of a company **with** a row in `payroll.overtime_settings` (without one, nothing is paid and `limite_horas_dobles_aplicado` stays 0; there is no silent default of 9). The calculation never looks at the checadas again: no decision, no pay.
- **Split.** Per employee, in chronological order: the first `limite_horas_dobles_periodo` hours are double and the rest triple. With the running sum of the previous days of the period (`SUM() OVER`), `horas_dobles = max(0, min(horas, limite - acumulado_previo))` and `horas_triples = horas - horas_dobles`; the day that crosses the limit is split. With limit 0 everything is triple. Days already paid by another period are excluded **before** the running sum, so they do not consume double hours of the current one.
- **Rate and rounding.** The hourly rate is `salario_diario / 8` with the operative `salario_diario` frozen in the same snapshot, times 2 (double) or 3 (triple). Each day is rounded on its own: `ROUND(horas_dobles x salario_diario x 2 / 8, 2)` and `ROUND(horas_triples x salario_diario x 3 / 8, 2)`; the intermediate rate is never rounded. The snapshot adds the already-rounded daily amounts, so the Detalle list matches to the cent, and the shown rate (`describeOvertimeHours`) is informative while the amount shown is always the stored one.
- **Tables.**
  - `payroll.period_employees` gains `horas_extra_dobles`, `horas_extra_triples`, `importe_horas_extra_dobles`, `importe_horas_extra_triples` and `limite_horas_dobles_aplicado` (all `NOT NULL DEFAULT 0`). `CK_period_employees_horas_extra` also guarantees `horas_extra_dobles <= limite_horas_dobles_aplicado`. **Snapshots from before spec 61 stay at 0** until they are recalculated.
  - `payroll.period_employee_overtime`: one row per paid day with the frozen `horas_autorizadas`, the double/triple split and both amounts. `ON DELETE CASCADE` to `period_employees` (Recalcular and Revertir free the days with the `DELETE` they already run, so `revertPayrollCalculation` did not change) and **no FK to `overtime_authorizations`**, so "Volver a pendiente" never collides with a paid day.
- **Pay-once lock.** `UQ_period_employee_overtime_empleado_fecha` is `UNIQUE (id_empleado, fecha)`: a day is paid once in the whole history, whatever the period, frequency or branch. It is not keyed by the authorization id, because deleting and authorizing again changes that id. `id_empleado` is repeated in the breakdown because `id_period_employee` changes on every recalculation. Two calculations competing for the same day end with one correct result and `describePayrollCalculationError` answers "Otro cálculo tomó algunas de estas horas extra al mismo tiempo. Intenta de nuevo." instead of a 500.
- **In the batch.** `#overtime_days` is built after `#product_sales`; the snapshot `INSERT` fills the five columns with an `OUTER APPLY` over it (only `tipo_nomina = 'O'`) and the breakdown is inserted from the same temp table joined to the new `'O'` rows, so both come from one set and cannot differ. The days of an employee who does not enter the operativa payroll of the period are neither paid nor blocked (they already show up in "empleados excluidos"). `lib/payroll/overtimePay.ts` (`splitOvertimeHours`, `calculateOvertimeDayAmounts`, `describeOvertimeHours`) restates the rule with strings, tenths of an hour and cents; if it diverges, the SQL is the source of truth.
- **"Recalcula" notice.** `isOvertimeRecalculationNeeded(id_period)` (`lib/payroll/overtimeRecalculation.ts`, server-only) is a single `SELECT` with `EXISTS`, only for periods at status 2, over the employees with an `'O'` snapshot row: an authorized day in the range that no period has paid; a breakdown day that is no longer authorized (rejected or back to pending); a breakdown day whose `horas_autorizadas` differ from the current authorization; or a current `limite_horas_dobles_periodo` different from `limite_horas_dobles_aplicado`. It is shown by the shared Server Component `nomina/componentes/PayrollRecalculationNotice.tsx` (renamed from `OvertimeRecalculationNotice` in spec 62, message as a prop) in Procesar (`overtimeRecalculationNeeded`) and Horas extra (`recalculationNeeded`): "Hay autorizaciones que no coinciden con el último cálculo. Recalcula la nómina." Salary changes do not trigger it, like the rest of the payroll. Comparing `decided_at` with `calculated_at` was discarded because it does not see the delete of "Volver a pendiente".
- **Screens.**
  - Procesar: "Horas extra" column after "Com. Ventas" (amount plus "Xh dobles · Yh triples" as secondary text, no secondary text without hours); "Total percepciones", the summary card and the footer add sueldo + the three commissions + overtime; the card and footer do not change with the puesto or search filters.
  - Detalle: `buildPerceptionLines` adds `horas_extra_dobles` ("Horas extra dobles", "X h x $rate") and `horas_extra_triples`, each omitted when its amount is 0; `PayrollOvertimeDaysList` (Server Component, no links) lists each paid day with date, authorized, double, triple and amount, plus a total row, and is hidden for fiscal or without paid days (`overtimeDays` is `[]`).
  - Horas extra: each day in `period_employee_overtime` shows the badge "Pagada en {código del periodo}" (`paidInPeriodCode`, from a separate query in `getOvertimePage` matched in TypeScript by `(id_empleado, fecha)`), and its decision can still be changed while the period is at status 1 or 2.
- **Consequences.** A paid day can still be rejected afterwards: nothing changes until the period is recalculated, and the notice says so. **No retroactive discount:** rejecting a day already paid in a period that later becomes Aprobada (3) or Pagada (4) does not revert anything; whoever builds those statuses must block decisions on paid days of periods 3 and 4. If an employee changes frequency and two periods of different frequency cover the same date, the lock pays the day only in the first period that is calculated, and each period applies its double limit only to the days it really takes. The days of someone excluded from the operativa payroll stay unpaid and unblocked.
- **Out of scope (later specs):** ISR (exempt the first 9 h, taxed after), fiscal payroll, SAT key and `payroll.perceptions`; a cap on triple hours, a per-calendar-week limit and configurable multipliers; recalculating only the overtime part or recalculating automatically when an authorization changes; paying the hours of someone outside the operativa payroll; releasing a paid day by hand; a global report of paid and pending hours; history of the applied limit beyond the spec 60 log; discounts for lateness or absences, prima dominical and worked rest days.
- **Known risks.** `calculatePayrollPeriod` chains the salary and three commissions with this concept, so any change to its `INSERT` or `WHERE` must be checked by comparing the snapshots of an already calculated period before and after. Salaries with many decimals make `salario_diario / 8` inexact in cents, which is why only the final daily amount is rounded.

## Faltas (spec 62)

Screen `/dashboard/nomina/faltas`; actions in `nomina/faltas/actions.ts`. Rules of origin: `references/docs/faltas.md` (section 3.1). Only absences are covered: lateness is spec 63 ("Retardos (spec 63)"); attendance/punctuality bonuses and holiday/vacation catalogs are separate specs.

- **Who is controlled.** An employee is reviewed when they enter **any** of the two payrolls of the period (`ELIGIBLE_ANY_PAYROLL_EMPLOYEE_CONDITIONS`: the base conditions plus `salario_diario > 0 OR salario_diario_fiscal > 0`) **and** have at least one linked user (`dbo.users.id_empleado`) with `id_role` in `ABSENCE_CONTROL_ROLE_IDS` (`[2]`, podólogo, in `lib/payroll/constants.ts`) and `status = 1` (`ABSENCE_CONTROLLED_EMPLOYEE_CONDITION`, one `EXISTS` shared by the screen, the writes, the calculation and the "Recalcula" notice). The role is evaluated **at the moment**, with no history. Everyone else never appears in Faltas or in its "Sin horario definido" notice and keeps `dias_falta = 0`. **A podólogo without a linked, active user is never controlled and gets no warning:** before calculating, check the Usuarios tab of the employee (spec 55).
- **What is an absence.** A day inside `max(fecha_inicio, fecha_ingreso)`..`fecha_fin`, strictly before today, with a row in `RH.empleado_horarios` for its ISO weekday and **no checada at all** in `RH.asistencias` (an incomplete checada counts as attendance: the missing punch already shows up in Horas extra). The **current** schedule is used for the whole period (no schedule history). An employee without a schedule generates no absences and appears in the "Sin horario definido" notice. Today comes as a string from `addZeroToday(new Date())`; SQL never uses `GETDATE()`.
- **Justification.** `payroll.absence_justifications` (`UNIQUE (id_empleado, fecha)`, no `id_period`, like `overtime_authorizations`): `estado 'J'` = justified with a PDF/JPG/PNG file of at most 5 MB (`url` must be a `https://res.cloudinary.com/` URL, uploaded through `/api/upload` with `utils/documentUpload.ts`), `'N'` = "No aplica" with a mandatory comment (holidays, vacations, "checador sin conexión"). **No row = unjustified.** Nobody approves a justification. `CK_absence_justifications_estado` enforces the shape of each state.
- **Writes** (`justifyAbsence`, `markAbsenceNotApplicable`, `clearAbsenceJustification`): `assertPayrollAccess`, `zod` schemas in `lib/payroll/schemas.ts`, and one transaction that reads the period `WITH (UPDLOCK, HOLDLOCK)`. The period/employee validation and the upsert are shared with Retardos in `lib/payroll/justificationWrites.ts` (`validateJustificationTarget`, `upsertJustification`). They re-validate branch, status 1 or 2, date in range, eligible + controlled employee and `fecha >= fecha_ingreso`; justify/no-aplica also require a date before today, a schedule that weekday and no checada. `clearAbsenceJustification` skips the day checks so a stale justification can always be cleaned. In periods 3 and 4 the screen is read-only and the actions return `{ ok: false }`.
- **Calculation.** `calculatePayrollPeriod` builds `#absences` (a recursive `period_days` CTE, `OPTION (MAXRECURSION 400)`) with the rules above, minus days with a justification row. In the snapshot `INSERT`, an `OUTER APPLY` counts, per employee and type, the absences that **no other period already discounted for that same `tipo_nomina`**; `dias_falta` gets that count, **`dias` becomes the net paid days (`calendar days - dias_falta`)** and `importe_salario = ROUND(salario x dias, 2)`. It applies to `'O'` **and** `'F'`, unlike the commissions. `payroll.period_employees` gains `dias_falta` (`NOT NULL DEFAULT 0`, `CK >= 0`); snapshots from before spec 62 have 0, so their `dias` is still right. Calendar days are `dias + dias_falta`.
- **Breakdown and lock.** `payroll.period_employee_absences`: one row per discounted absence with `id_period_employee`, `id_empleado`, `tipo_nomina`, `fecha`. `UNIQUE (id_empleado, fecha, tipo_nomina)`: the same day is discounted once per payroll type, never twice in the same type, whatever the period. `ON DELETE CASCADE` to `period_employees` (Recalcular and Revertir free the days with the `DELETE` they already run, so `revertPayrollCalculation` did not change) and **no FK to `absence_justifications`**, so justifying an already discounted day never collides. Two competing calculations end with `describePayrollCalculationError` answering "Otro cálculo tomó algunas de estas faltas al mismo tiempo. Intenta de nuevo."
- **Source of truth.** `lib/payroll/absenceDetection.ts` (`detectEmployeeAbsences`, `formatIsoWeekday`, pure, strings only) feeds the screen. If it diverges from the SQL in the calculation, **the SQL wins**. The ISO weekday in SQL is `(DATEDIFF(day, '19000101', fecha) % 7) + 1` (1900-01-01 was a Monday), independent of `DATEFIRST`.
- **"Recalcula" notice.** `isAbsenceRecalculationNeeded(id_period)` (`lib/payroll/absenceRecalculation.ts`, server-only), only at status 2, compares the set of absences that would be discounted **today** with the period's breakdown: an absence of today that no period discounted for a row type of this period, or a discounted absence that is no longer an absence (justified, new checada, schedule change, the employee lost the active podólogo user). "Volver a injustificada" is a `DELETE` that leaves no trace, which is why `decided_at` vs `calculated_at` was discarded. It uses the shared `nomina/componentes/PayrollRecalculationNotice.tsx` (message as a prop) in Procesar (`absenceRecalculationNeeded`) and Faltas (`recalculationNeeded`): "Hay faltas que no coinciden con el último cálculo. Recalcula la nómina."
- **Screens.**
  - Faltas: Server Component with state in the URL (`periodo`, `estado=injustificada|justificada|no_aplica`, `q`, `pagina`), 25 rows per page (`ABSENCE_PAGE_SIZE`). Summary cards cover the whole period and do not change with the filters. Rows show the badge "Descontada en {código}" (`discountedInPeriodCodes`). Client components are limited to `AbsenceToolbar` (a wrapper over the shared `PayrollPeriodFilterToolbar`), and the shared justification components in `nomina/componentes/` (`JustificationUploadModal`, `NotApplicableModal`, both on `JustificationModalFrame` and rendered through a portal, plus `ClearJustificationButton` with in-UI confirmation and no native `confirm()`). Since spec 63 they are generic: they receive the server action, the Cloudinary folder (`clinica/empleados/faltas`) and the texts as props, and Retardos reuses them. `AbsenceDaysTable` (Server Component) builds their props.
  - Procesar: the "Días" column shows "F faltas" below the days when `dias_falta > 0`.
  - Detalle: the `sueldo_base` line reads "13 días (15 − 2 faltas) × $X diarios" (the amount is always the stored one) and `PayrollAbsencesList` (Server Component, hidden when empty) lists the discounted dates of the selected type (`discountedAbsences`).
- **Consequences.** **No retroactive discount:** justifying a day already discounted in a period that later becomes Aprobada (3) or Pagada (4) reverts nothing; whoever builds those statuses must block justifications of discounted days in periods 3 and 4. A checador that stops sending punches makes every controlled employee of the branch look absent that day: review Faltas before "Calcular" and mark those days "No aplica" with a comment. Holidays are not detected (no catalog): use "No aplica". Files replaced or orphaned in Cloudinary are not deleted. Changing an employee's schedule changes how past days are detected (the notice catches it at status 2).
- **Out of scope:** lateness (now spec 63), attendance/punctuality bonuses, holiday/vacation/sick-leave catalogs, second-user approval of justifications, other roles or per-employee configuration, schedule history, bulk justification, manual entry of undetected absences, showing absences in the employee's Asistencia tab, and deductions as their own concept (IMSS, ISR, "Total a pagar").
- **Known risks.** `calculatePayrollPeriod` now also chains this concept, so any change to its `INSERT` or `WHERE` must be checked by comparing the snapshots of an already calculated period before and after. If the calculation gets slow, add an index on `RH.asistencias(id_empleado, fecha_hora)` without changing the logic.

## Retardos (spec 63)

Screen `/dashboard/nomina/retardos`; actions in `nomina/retardos/actions.ts`. Rules of origin: `references/docs/faltas.md` (section 3.2). It is the sibling of Faltas and reuses most of it. Only arrival lateness against `hora_entrada_1` is covered: the return from the second block (`hora_entrada_2`), early departures and punctuality/attendance bonuses are separate specs.

- **Who is controlled.** The same population as Faltas: `ELIGIBLE_ANY_PAYROLL_EMPLOYEE_CONDITIONS` + `ABSENCE_CONTROLLED_EMPLOYEE_CONDITION` (a linked, active user with `id_role` 2, evaluated at the moment). There is no separate constant: if the two rules ever diverge, split it then. Same caveat as Faltas: **a podólogo without a linked, active user is never controlled and gets no warning**.
- **What is lateness.** A day inside `max(fecha_inicio, fecha_ingreso)`..`min(fecha_fin, today)` (**today included**: a delay is final as soon as the entry punch exists), with a row in `RH.empleado_horarios` for its ISO weekday, at least one punch of `tipo = 'entrada'` (the **first** one is the arrival) and `minutos = floor((arrival - hora_entrada_1) / 60 s)` greater than or equal to `tolerancia_minutos`. Seconds are truncated (08:09:59 is 9 minutes). Only `hora_entrada_1` is compared. A day without any `entrada` (only `salida`) is not evaluated, and a day without punches is Faltas' business, so a day can never be both. The **current** schedule is used for the whole period. Rest days (no schedule row) are never evaluated. An employee without a schedule generates no lateness and appears in the "Sin horario definido" notice.
- **Classification.** `minutos >= minutos_retardo_grave` is **severe** (`'G'`), otherwise **accumulable** (`'A'`). They are mutually exclusive: a severe delay never counts toward the accumulation tiers.
- **Configuration per company, with a change log.** `payroll.lateness_settings` (one row per company, PK `id_empresa`): `tolerancia_minutos` (seed 10), `minutos_retardo_grave` (seed 30) and `dias_descuento_retardo_grave` (0.5 or 1, seed 0.5). `payroll.lateness_tiers` holds the accumulation tiers per company and frequency (`id_payment_period`, `retardos`, `dias_descuento`; seeds: weekly SAT `02` {1 -> 0.5, 2 -> 1}, biweekly SAT `04` {2 -> 0.5, 4 -> 1}). `payroll.lateness_settings_log` stores every change; the tiers go in the log as JSON because their number varies. **A company without a row in `lateness_settings` discounts nothing** (no silent default, like overtime); a frequency without tiers discounts only severe delays and the screen shows "Sin escalones para {frecuencia}". `updateLatenessSettings` runs in one transaction that reads the row `WITH (UPDLOCK, HOLDLOCK)`, validates (`updateLatenessSettingsSchema`: tolerance a positive integer, severe threshold greater than the tolerance, severe discount 0.5 or 1, tiers without repeated `retardos` per frequency, `dias_descuento` a multiple of 0.5 and **not decreasing** as `retardos` grows, since a CHECK cannot compare rows), replaces the tiers, updates `updated_at` and writes the log. **Saving without changes writes nothing.** `updated_at` moves on any change, even if only the tiers changed: the "Recalcula" notice depends on it.
- **Discount** per employee and payroll type, counting only unjustified delays that **no other period already discounted for that `tipo_nomina`**: severe delays `G x dias_descuento_retardo_grave`, plus the accumulable ones through the tiers of the period's frequency **in cycles**: `ciclo = MAX(retardos)`, `floor(A / ciclo) x dias_descuento of the top tier + dias_descuento of the highest tier with retardos <= A mod ciclo` (0 if none). With {1 -> 0.5, 2 -> 1}, three accumulable delays are 1.5 days; with {2 -> 0.5, 4 -> 1}, five are 1 and six are 1.5. `dias_retardo = min(sin tope, dias)` (the salary never goes negative) and `importe_salario = ROUND(salario x (dias - dias_retardo), 2)`, in `'O'` **and** `'F'`. `payroll.period_employees` gains `dias_retardo decimal(4,1)` and `dias_retardo_sin_tope decimal(5,1)` (`NOT NULL DEFAULT 0`, `CK_period_employees_dias_retardo`). **`dias` keeps its meaning** (net days after absences, an integer).
- **Justification.** `payroll.lateness_justifications`, the same shape as `absence_justifications` (`UNIQUE (id_empleado, fecha)`, no `id_period`): `'J'` with a PDF/JPG/PNG of at most 5 MB in the Cloudinary folder `clinica/empleados/retardos`, or `'N'` "No aplica" with a mandatory comment ("reloj del checador desfasado", "entrada mal registrada"). **No row = unjustified.** It is a sibling table on purpose: reusing `absence_justifications` with a type column would let a punch arriving on a day justified as an absence be read as a lateness justification.
- **Writes** (`justifyLateness`, `markLatenessNotApplicable`, `clearLatenessJustification`): `assertPayrollAccess`, `zod` (`justifyLatenessSchema` and its siblings are aliases of the Faltas schemas), one transaction with the shared `validateJustificationTarget` (branch, status 1 or 2, date in range, eligible + controlled employee, `fecha >= fecha_ingreso`). Justify and no-aplica also require `fecha <= today`, a settings row, a schedule that weekday, an `entrada` punch and that the first one is at least `tolerancia_minutos` late (`validateDayIsLateness`, evaluated with the **current** tolerance). `clearLatenessJustification` skips the day checks. In periods 3 and 4 the screen is read-only and the actions return `{ ok: false }`.
- **Calculation.** `calculatePayrollPeriod` builds `#lateness` after `#absences` (same recursive `period_days` CTE) with the rules above, minus days with a justification row. **Accumulable delays only enter `#lateness` if the company has tiers for the period's frequency**, so a frequency without tiers neither discounts them nor locks the day for another period; severe ones always enter. The snapshot `INSERT` counts graves and accumulables per employee and type through an `OUTER APPLY` (omitting what another period already discounted for that type), resolves the cycle from `lateness_tiers` and fills `dias_retardo`, `dias_retardo_sin_tope` and `importe_salario`. A company without `lateness_settings` gets zeros. The minutes are truncated with `CONVERT(varchar(8), llegada, 108)` and `DATEDIFF(second, ...) / 60`; the ISO weekday is `(DATEDIFF(day, '19000101', fecha) % 7) + 1`.
- **Breakdown and lock.** `payroll.period_employee_lateness`: one row per discounted delay with `id_period_employee`, `id_empleado`, `tipo_nomina`, `fecha` and the frozen `hora_entrada_1`, `hora_llegada`, `minutos_retardo` and `clasificacion`, so the Detalle explains the discount even if the schedule or the configuration change later. `UNIQUE (id_empleado, fecha, tipo_nomina)`, `ON DELETE CASCADE` to `period_employees` (Recalcular and Revertir free the days with the `DELETE` they already run) and **no FK to `lateness_justifications`**. Two competing calculations end with "Otro cálculo tomó algunos de estos retardos al mismo tiempo. Intenta de nuevo."
- **Source of truth.** `lib/payroll/latenessDetection.ts` (`detectEmployeeLateness`, `classifyLateness`, `calculateLatenessMinutes`, `calculateLatenessDiscountDays`, pure, strings only) feeds the screen. If it diverges from the SQL in the calculation, **the SQL wins**.
- **"Recalcula" notice.** `isLatenessRecalculationNeeded(id_period)` (`lib/payroll/latenessRecalculation.ts`, server-only), only at status 2, is true when: (1) a delay of today would be discounted for a row type of this period and no period discounted it; (2) a discounted delay is no longer a delay or changed classification (justified, another tolerance or severe threshold, new punch, schedule change, the employee lost the active podólogo user); (3) `lateness_settings.updated_at` is later than `MIN(calculated_at)` of the period (tiers or severe discount edited, which do not change the set). Comparing `decided_at` against `calculated_at` for justifications was discarded (it misses deletes); for the configuration it is valid because saving is always an `UPDATE`. Shown with `PayrollRecalculationNotice` in Procesar (`latenessRecalculationNeeded`) and Retardos (`recalculationNeeded`): "Hay retardos que no coinciden con el último cálculo. Recalcula la nómina."
- **Screens.**
  - Retardos: Server Component with state in the URL (`periodo`, `estado=injustificado|justificado|no_aplica`, `tipo=grave|acumulable`, `q`, `pagina`), 25 rows per page (`LATENESS_PAGE_SIZE`). Summary cards and the per-employee summary (severe, accumulable and estimated days before the cap) cover the whole period and do not change with the filters. Rows show scheduled time, first entry, minutes late, type, status, file or comment and the badge "Descontado en {código}". The settings card, its edit modal (`LatenessSettingsModal`, a portal with the three fields and a tier editor per frequency) and the change log (a `<details>`) sit above the list; the configuration can be edited at any time, the justification actions only with the period at status 1 or 2. Client components: `LatenessToolbar` (a wrapper over `PayrollPeriodFilterToolbar`, which gained an optional `extraFilter` for `tipo`), `LatenessSettingsModal` and the shared justification components of Faltas.
  - Procesar: the "Días" column shows "R retardo" below the days when `dias_retardo > 0`, next to "F faltas".
  - Detalle: the `sueldo_base` line reads "11.5 días (15 − 2 faltas − 1.5 por retardos) × $X diarios", with "(tope aplicado)" when `dias_retardo_sin_tope > dias_retardo`, and `PayrollLatenessList` (Server Component, hidden when empty) lists date, scheduled time, arrival, minutes and type of the delays discounted for the selected type (`discountedLateness`).
- **Consequences.** **No retroactive discount:** justifying a delay already discounted in a period that later becomes Aprobada (3) or Pagada (4) reverts nothing; whoever builds those statuses must block those justifications. **A checador with a skewed clock** (say 15 minutes fast) produces false delays in bulk for the whole branch, and a checador that sends a wrong `tipo` can make a later `entrada` (the return from lunch) look like the arrival, giving a false severe delay: review Retardos before "Calcular" and mark those days "No aplica" with a comment. Changing an employee's schedule changes how past days are detected (the notice catches it at status 2). Changing the configuration affects every period of the company that is not yet approved, not only the current one. Extreme tiers (say 1 delay -> 3 days) can leave the base salary at zero; the cap and the change log mitigate it. Files replaced or orphaned in Cloudinary are not deleted.
- **Out of scope:** the return from the second block and early departures, punctuality/attendance bonuses, delays on rest days, configuration per branch or employee, other roles, second-user approval and bulk justification, schedule history, retroactive discount in periods 3 and 4, deleting Cloudinary files, showing delays in the employee's Asistencia tab, a holiday catalog and deductions as their own concept (IMSS, ISR, "Total a pagar").
- **Known risks.** `calculatePayrollPeriod` now chains salary, three commissions, overtime, absences and lateness, so any change to its `INSERT` or `WHERE` must be checked by comparing the snapshots of an already calculated period before and after (deleting `lateness_settings` inside a transaction that is rolled back is a safe way to prove that a period without delays stays identical). If it gets slow, add an index on `RH.asistencias(id_empleado, fecha_hora)` without changing the logic.

## Detalle por empleado (spec 54)

Screen `/dashboard/nomina/procesar/[id_empleado]?periodo=ID&tipo=operativa|fiscal&puesto=&q=`; action `getPayrollEmployeeDetail(filters)` in `nomina/procesar/actions.ts`. Read-only: it reads `payroll.period_employees`, `payroll.period_employee_treatments`, `payroll.period_employee_product_sales`, `payroll.periods`, `RH.empleados` and `RH.puestos` (plus `Tratamiento_onicomicosis`, `consultas` and `pacientes` for the paid-treatments list, and `inventory.Products` for the product names of the sold-products list).

- **Parameters:** `periodo` is required (no "current period" guessing). `tipo` defaults to `operativa`. `puesto` and `q` are only carried over for "Regresar" and Anterior / Siguiente. URLs are built with `buildPayrollProcessHref` / `buildPayrollEmployeeDetailHref` in `lib/payroll/processUrls.ts` (which also holds the `searchParams` readers shared with Procesar); empty or `null` params are omitted.
- **404 (`notFound()`)**: missing or non-numeric `periodo` or `id_empleado`, a period from another branch or nonexistent, or an employee that is neither from the period's branch nor has a snapshot row in the period. The snapshot rule keeps the detail reachable for someone who changed branch after the calculation.
- **What it shows:** breadcrumb, "Detalle de Nómina" with the period code, "Regresar", Anterior / Siguiente, the Operativa | Fiscal toggle (links, in the URL), the employee card (`EmployeeAvatar`, name, code, puesto, `EmployeeStatusBadge`, daily salary of the selected type from the snapshot, period range and payment date) and the "Percepciones totales" card (total, concept count, one row per line).
- **Perception lines:** built by `buildPerceptionLines(snapshot, fechaIngreso, fechaInicio, commissionTiers)` in `lib/payroll/perceptionLines.ts`. It returns `sueldo_base` and, when the amount is `> 0`, `comision_consultas` (spec 56), `comision_tratamientos` (spec 57), `comision_productos` (spec 58), `horas_extra_dobles` and `horas_extra_triples` (spec 61, "X h x $rate" from the frozen daily salary, each omitted when its amount is 0). `sueldo_base` ("N días × $X diarios", or "N días (calendar − F faltas − R por retardos) × $X diarios" when there are absences or lateness, plus "(tope aplicado)" when the lateness discount was capped; the paid days are `dias - dias_retardo`; amount = `importe_salario` as stored, never recalculated in TS) with the note "Ingresó el DD/MM/AAAA, proporcional" when `fecha_ingreso > fecha_inicio` (string comparison, no `Date`). **New concepts (bonuses, …) are added there as new lines**; the card iterates the list and needs no layout change.
- **States:**
  - Period at status 1: notice "Esta nómina aún no se calcula" with a link to Procesar; no perceptions card and no Anterior / Siguiente.
  - No snapshot row for the selected type (status 2+): notice "Este empleado no está en la nómina {operativa|fiscal} de este periodo"; the toggle and employee card stay, daily salary shows "—", no Anterior / Siguiente.
- **Anterior / Siguiente:** `LAG`/`LEAD` over the snapshot of the same period and type, with the same puesto/search conditions (`buildPayrollEmployeeConditions`, shared with `getPayrollProcessPage`) and the same `ORDER BY` (`PAYROLL_EMPLOYEE_ORDER_BY`: `apellido_paterno, apellido_materno, nombre, id_empleado`). At either end the button is a non-link `<span aria-disabled="true">`. If the employee is not in the filtered set, there is no navigation.
- **Components** (`procesar/[id_empleado]/componentes/`, all Server Components, no `"use client"`): `PayrollEmployeeProfileCard`, `PayrollPerceptionsCard`, `PayrollPaidTreatmentsList` (spec 57, hidden when empty), `PayrollSoldProductsList` (spec 58, hidden when empty), `PayrollOvertimeDaysList` (spec 61, hidden when empty), `PayrollAbsencesList` (spec 62, hidden when empty), `PayrollLatenessList` (spec 63, hidden when empty), `PayrollTypeToggle`, `PayrollEmployeeNavigation`, `PayrollDetailNotice`. `EmployeeAvatar` lives in `empleados/componentes/` and is shared with the employee record header.
