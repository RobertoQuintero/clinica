# HR — Employees (empleados)

- `app/dashboard/empleados/` covers employee onboarding, listing, and detail (`RH.empleados` table; catalogs in `interfaces/rh_catalogs.ts` — department, puesto, turno).
- Employee detail (`empleados/[id]/`) is a tabbed layout: **Documentos** (`[id]/documentos/`, Cloudinary uploads), **Asistencia** (`[id]/asistencia/`, attendance records fed by the biometric checadores — see `docs/asistencias-biometricas.md`), **Horario** (`[id]/horario/`, weekly schedule), **Vacaciones** (`[id]/vacaciones/`, yearly entitlement and vacation block — spec 76), **Días económicos** (`[id]/dias-economicos/`, up to 3 days per calendar year — spec 79) and **Usuarios** (`[id]/usuarios/`).

## Usuarios tab (`empleados/[id]/usuarios/`)

- Links system accounts (`dbo.users`) to an employee through `users.id_empleado` (nullable FK to `RH.empleados`, non-unique index). A user belongs to at most one employee; an employee can have several users. There is no bridge table and no link history.
- The tab is a Server Component listing **all** linked users (including those later set to `status = 0`), with a per-row "Desvincular" button. Only `LinkUserModal.tsx` and `UnlinkUserButton.tsx` are Client Components. Access is already covered by `proxy.ts` for `/dashboard/empleados` (roles 1 and 4).
- **Eligibility to link:** same `id_empresa` as the employee, `status = 1`, and `id_empleado IS NULL`. Branch (`sucursal`) and `id_role` do not restrict. Linking an employee with `activo = 0` is allowed.
- **Server actions** (`usuarios/actions.ts`, schemas in `usuarios/schemas.ts`): `getEmployeeLinkedUsers`, `getLinkableUsers`, `linkUserToEmployee`, `unlinkUserFromEmployee`. The two writes parse with `zod`, re-validate against the DB, and repeat the link condition in the `UPDATE ... WHERE` (`IS NULL` when linking, `= @id_empleado` when unlinking) with `OUTPUT INSERTED`, so a concurrent change affects zero rows and returns `{ ok: false }`.
- **Unlinking** sets `id_empleado = NULL` and keeps the user's access, role and branch. **Deactivating an employee does not unlink** their users.
- `/dashboard/usuarios` shows a read-only, sortable "Empleado" column (`getUsuarios` does a `LEFT JOIN` on `RH.empleados`). `saveUsuario` lists its columns explicitly and never touches `id_empleado`.
- **Not implemented yet:** `users.id_empleado` is only the foundation for attributing commissions (sales, consultations, treatments) and feeding payroll. No calculation or report uses the link today.

## Horario tab (`empleados/[id]/horario/`)

- Stores the employee's expected weekly schedule in `RH.empleado_horarios` (DDL in `queries.txt`, block `RECURSOS HUMANOS(EMPLEADOS)`): **one row per worked day**, ISO `dia_semana` (1 = Monday … 7 = Sunday), up to two blocks per day (`hora_entrada_1/hora_salida_1`, optional `hora_entrada_2/hora_salida_2`, for split shifts). **A day without a row is a rest day.** `UNIQUE (id_empleado, dia_semana)` prevents duplicates. Shifts cannot cross midnight.
- **CHECK constraints** repeat the validation rules in the DB (block 1 exit > entry; block 2 is either fully NULL or fully set, starts strictly after block 1 ends, and exits after its entry). The block 2 branch carries explicit `IS NOT NULL` checks: without them a half-filled block evaluates to `UNKNOWN` and a `CHECK` lets `UNKNOWN` through.
- **Saving replaces the whole week**: `saveEmployeeSchedule` (`horario/actions.ts`) validates with `zod` (`horario/schemas.ts`, `server-only`), then runs `DELETE` + one `INSERT` per day inside `db.transaction`, so a failure leaves the previous schedule intact. There is **no history and no effective dates**; saving an empty week is allowed and means "Sin horario definido". `EditScheduleModal.tsx` mirrors the same rules client-side through the pure `scheduleValidation.ts` (the zod schema can't be imported in the client).
- **Times are strings, never `Date`**: `time(0)` columns are read with `CONVERT(varchar(5), [col], 108)` (`"HH:mm"`; otherwise mssql returns a `Date`) and written as `"HH:mm"` strings through `queryParams`. `created_at` uses `buildDate(new Date())`; `IEmployeeSchedule.updated_at` is `MAX(created_at)`.
- The page is a Server Component; `EditScheduleModal.tsx` is the only Client Component. `scheduleFormatting.ts` (pure) holds the weekday labels, `calculateWeeklyHours` and `formatScheduleSummary` (e.g. `Lun–Vie 09:00–18:00 · Sáb 09:00–14:00`), also used by the "Horario" row in `EmployeeGeneralInfo.tsx`. Access is covered by `proxy.ts` for `/dashboard/empleados` (roles 1 and 4), so anyone who can open the tab can edit.
- **Legacy free text:** `RH.empleados.dias_laborales` / `horario` are no longer captured. They stay in `IEmployee` and the SELECT, are excluded from `EmployeeFormInput`, and `createEmployee`/`updateEmployee` don't write them (editing an employee never alters the old text). The Horario tab shows them read-only as "Referencia anterior" only while the employee has no structured schedule. They are not migrated automatically.
- **Independent of `id_turno`:** the `RH.turnos` catalog and the "Turno" select are unrelated to this schedule.
- **Used by payroll:** the schedule feeds overtime detection (spec 60) and absence detection (spec 62; a day with a row is a working day, without a row it is a rest day). **Not implemented yet:** lateness and tolerances. Because the schedule has no effective dates, both specs evaluate past periods against the *current* schedule, so changing it changes how past days are detected (the payroll "Recalcula" notice catches it while the period is at status 2); validity ranges would be needed to avoid that.

## Vacaciones (spec 76)

- **Tab** `empleados/[id]/vacaciones/` (Server Component page; the only Client Components are `VacationBlockModal`, `VacationReasonModal` and `MarkVacationPaidModal`). One **year of entitlement** per employee and anniversary, a **single continuous block** per year, and a manual "paid" mark for the days not taken. **Payroll (spec 78):** the payment date of the surplus days decides the payroll period that pays them, and the vacation premium (25% over all the entitled days, paid once per year) is paid by the period that contains `fecha_inicio` of the block (or `fecha_pago` when there is no block); see "Vacaciones y prima vacacional" in `docs/nomina.md`. Since spec 77 the days inside a captured block are excluded from absences, lateness and the punctuality/attendance bonuses (see "Exclusión de vacaciones (spec 77)" in `docs/nomina.md`); there is no need to mark them "No aplica".
- **Tables** (DDL in `queries.txt`, block `RECURSOS HUMANOS(EMPLEADOS)`, `RH` schema): `vacation_days_by_seniority` (LFT catalog, 14 ranges seeded idempotently, 46–50 years = 38 days; no edit UI), `vacation_entitlements` (`UNIQUE (id_empleado, anio_servicio)`; `dias_derecho` and the three dates are a **snapshot**; "all-or-nothing" `CHECK`s for the block and for the payment) and `vacation_entitlement_log` (`'C'` capture, `'R'` reschedule, `'X'` cancel, `'P'` pay, `'V'` revert; reason required in `R/X/V`). Every write and its log row go together in `db.transaction`.
- **Generation**: `syncVacationEntitlements(id_empresa, id_empleado?)` (`lib/vacations/entitlementSync.ts`, `server-only`) is one idempotent `INSERT … SELECT … WHERE NOT EXISTS`, run when the employee list (`getEmployees`) or the detail layout opens. Active employees only; with no rows it creates just the **current year** (last anniversary completed, no backfill); with rows it creates every later anniversary. Never throws (logs and keeps rendering). Changing `fecha_ingreso` does not alter existing years. Employees past 50 years of service get no year (no catalog range).
- **Status is derived, there is no `estado` column**: `lib/vacations/vacationStatus.ts` (`getVacationStatus`, `getDaysToPay`, `getVacationBadgeSummary`) computes it from the row and today's date in Mexico City. `pendiente` (no block, today ≤ `fecha_limite_solicitud`), `programada`, `en_curso`, `tomada`, `por_pagar` (block ended with days left, or deadline passed without a block) and `pagada`. Surplus days become payable when the block **ends**.
- **Rules** (`vacaciones/actions.ts`, schemas in `vacaciones/schemas.ts`; every write re-checks the state in the `UPDATE … WHERE … OUTPUT` so a concurrent write affects 0 rows and returns `{ ok: false }`, and repeats the roles 1/4 gate via `assertVacationAccess` because server actions can be invoked without going through `proxy.ts`):
  - `scheduleVacationBlock`: current year, no block, capture on or before `fecha_limite_solicitud` (the block itself may fall after it), `fecha_inicio ≥ fecha_aniversario`, `fecha_fin < fecha_siguiente_aniversario` (not cumulative), past dates allowed. **`fecha_fin` is always recomputed on the server** (`calculateVacationEndDate`, counting only days with a row in `RH.empleado_horarios`) and is a snapshot: a later schedule change does not move it. Without a schedule it cannot be captured.
  - `rescheduleVacationBlock` / `cancelVacationBlock`: only while `fecha_inicio > today` and unpaid, reason required; rescheduling ignores the deadline and keeps `solicitado_at`. Cancelling after the deadline leaves the year `por_pagar` (it cannot be captured again).
  - `markVacationDaysPaid` / `revertVacationPayment`: only in `por_pagar`; `dias_pagados` is computed by the database (`dias_derecho − dias_tomados`, enforced by a `CHECK`), never sent by the client; revert needs a reason.
- **Payroll status (spec 78, read only)**: `getEmployeeVacations` also reads `payroll.period_employee_vacations` and returns `payroll_payments`, `premium_status` (`pagada` / `pendiente` / `sin_evento`) and `paid_days_in_payroll`; `VacationPayrollStatus` shows "Prima: Pagada en {código}" / "Pendiente" / "—" and "Días: Pagados en {código}" / "Marcados, sin nómina calculada" in the current-year card and the history. `MarkVacationPaidModal` calls `getPayrollPeriodForDate({ id_empleado, fecha })` (the branch's period of the employee's payment frequency that contains the date) and shows "Se pagará en {código}" or an amber "Ningún periodo contiene esta fecha"; saving is allowed either way. Cancelling, rescheduling, reverting and re-marking are **not** blocked by an already calculated period: the payroll "Recalcula" notice flags it.
- **Where it shows**: current-year card and history (with the log, `<details>`) in the tab; `VacationStatusBadge` in `EmployeeHeader` (via `getCurrentVacationStatus`) and in `EmployeeRow`; "Vacaciones pendientes" card in `EmployeeSummaryCards` (`pendiente` + `por_pagar`). The badge is amber when `pendiente` with 30 days or fewer to the deadline and red in `por_pagar`. The list gets the current year with an `OUTER APPLY` in `getEmployees`.
- **Known gaps**: the law (art. 79 LFT) forbids paying vacations in cash except at termination; "por pagar" implements the client's rule, not the law (since spec 78 the payment also reaches payroll and the CFDI). No holiday catalog (a holiday inside a block counts as a vacation day), no schedule history, no termination-time proportional vacations.

## Días económicos (spec 79)

- **Tab** `empleados/[id]/dias-economicos/` (Server Component page; the only Client Components are `RegisterEconomicDayModal` and `CancelEconomicDayModal`), placed after Vacaciones. Each employee has up to `ECONOMIC_DAYS_PER_YEAR = 3` (`lib/economicDays/economicDayRules.ts`) economic days per **calendar year** (Jan 1 – Dec 31, Mexico City time). The balance is derived from the year of `fecha` (no per-year rows, no cron: it resets by itself on Jan 1). Unused days are lost; they are not paid or accumulated.
- **Table** `RH.economic_days`: one row per day. Cancelling does not delete: it fills `cancelado_by` / `cancelado_at` / `motivo_cancelacion` (all or none, `CHECK`), so the row is the audit log. The filtered unique index `UX_economic_days_empleado_fecha_activo` (`WHERE cancelado_at IS NULL`) allows only one active day per employee and date, and a cancelled date can be registered again. The limit of 3 cannot be a `CHECK` (it would have to count rows), so it lives in the `INSERT`.
- **Rules** (`dias-economicos/actions.ts`, schemas in `dias-economicos/schemas.ts`; both writes repeat the roles 1/4 gate via `assertVacationAccess` and validate with `zod`):
  - `registerEconomicDay`: active employee; `fecha` in the current calendar year (past or future); `fecha` is a working day of `RH.empleado_horarios` (no schedule → cannot register, "Sin horario definido"); `fecha` is not inside a captured vacation block; motivo required (max 500). The duplicate-date and balance checks are one `INSERT … SELECT … WHERE NOT EXISTS (…) AND (SELECT COUNT(*) … WITH (UPDLOCK, HOLDLOCK)) < 3 OUTPUT INSERTED` inside `db.transaction`, so two simultaneous captures cannot exceed 3; 0 rows returns `{ ok: false }`.
  - `cancelEconomicDay`: any active day of the current year, past or future, with a required motivo; the `UPDATE … WHERE cancelado_at IS NULL AND fecha` in the current year affects 0 rows otherwise. To change a date, cancel and register another.
  - Previous years are read-only (a December day not captured in time cannot be regularized in January). An inactive employee shows the history, hides both actions, and the actions reject the write.
- **Vacations cross-check**: `scheduleVacationBlock` and `rescheduleVacationBlock` reject a block whose `fecha_inicio..fecha_fin` contains an active economic day ("El bloque incluye un día económico registrado el {fecha}. Cancélalo primero."), using `findActiveEconomicDayInRange` / `ACTIVE_ECONOMIC_DAY_IN_RANGE_SQL` from `lib/economicDays/economicDaySql.ts`. The reverse is the check in `registerEconomicDay`, so an economic day is never spent on a vacation day.
- **Shared UI**: `EmployeeWithoutScheduleNotice` (`empleados/[id]/componentes/`) is the "Sin horario definido" notice shared by Vacaciones and Días económicos.
- **Payroll**: an active economic day is excluded from absences, lateness and both bonuses, and is paid as a worked day (spec 80, see `docs/nomina.md` "Exclusión de días económicos (spec 80)").
- **Known gaps**: no biometric-device validation change, no request/approval flow for the employee, no half days, no proration or minimum seniority, no holiday catalog (a day can be spent on a holiday), and the schedule is validated only at capture time (a later schedule change does not revalidate the day; RH can cancel it).

## Datos fiscales (spec 71)

- **Purpose:** capture and validate the receiver data the CFDI 4.0 + Nómina 1.2 complement require, and show in the employee record what is still missing. **Stamping itself is not implemented** (see "Not implemented yet").
- **Columns** (`RH.empleados`, DDL in `queries.txt`, block `RECURSOS HUMANOS(EMPLEADOS)`, all `NULL`): `codigo_postal_fiscal char(5)` (`DomicilioFiscalReceptor`), `tipo_regimen` (`c_TipoRegimen`), `tipo_contrato` (`c_TipoContrato`), `tipo_jornada` (`c_TipoJornada`), `sindicalizado bit` (`NULL` is sent as "No") and `banco char(3)` (FK to `RH.cat_bancos.clave`). `rfc`, `curp`, `nss` and `cuenta_bancaria` keep their type and only gain `CHECK`s. Existing employees got `02/01/01/0` for regime/contract/workday/union in a one-off `UPDATE`.
- **Catalogs:** `c_Banco` is the table `RH.cat_bancos` (`clave`, `nombre`, `razon_social`, `status`; ~93 rows, loaded by hand, so it must be checked against the current SAT file). `c_TipoContrato`, `c_TipoRegimen` and `c_TipoJornada` are TypeScript constants in `lib/payroll/satCatalogs.ts` and are backed in the DB by `CHECK ... IN (...)`; changing one means editing both. That file also holds `PAYROLL_RECEIVER_TAX_REGIME = '605'`, `PAYROLL_CFDI_USE = 'CN01'` (unused until stamping) and `DEFAULT_EMPLOYEE_FISCAL_VALUES` (prefilled on create).
- **`CHECK` constraints** (10, created `WITH NOCHECK`): format of `rfc` (13-char natural person), `curp`, `nss` (11 digits), `codigo_postal_fiscal` (5 digits) and `cuenta_bancaria` (10, 11, 16 or 18 digits); the three catalog `IN` lists; `CK_empleados_banco_sin_clabe` (no `banco` with an 18-digit CLABE or without account) and `CK_empleados_contrato_regimen` (contract 01–08 ⇒ regime 02–04; contract 09/10/99 ⇒ any other regime). `WITH NOCHECK` means existing rows are not validated but **every later `INSERT`/`UPDATE` is**, so a legacy row with a bad value cannot be saved by any path (including raw SQL) until it is corrected. The TS regexes and the `LIKE` patterns are written from the same case list; if they differ, the DB wins.
- **Who is "fiscal":** `salario_diario_fiscal > 0` (same rule that puts an employee in the fiscal payroll, spec 53). Only fiscal employees are required to be complete; **formats are validated whenever a value is present**, fiscal or not.
- **Required for a fiscal employee** (`getRequiredStampingFields`): always `rfc`, `curp`, `codigo_postal_fiscal`, `tipo_contrato`, `tipo_regimen` and `id_periodo_pago`; plus `nss` and `tipo_jornada` when the regime is 02, 03 or 04; plus `banco` when the account has 10, 11 or 16 digits. An 18-digit CLABE carries **no** bank (the SAT forbids sending `Banco` with a CLABE), and the server forces `banco = NULL` even if the client sends one.
- **Pure rules** live in `lib/payroll/payrollStampingReadiness.ts` (importable from client and server): patterns, normalizers, `isFiscalEmployee`, `getRequiredStampingFields` (modal asterisks) and `getStampingIssues(employee, branchStateKey)` (employee record; `[]` = ready to stamp). The input type is `StampingEmployeeInput`, which `EmployeeFormInput` and `IEmployeeRecord` satisfy structurally.
- **Server validation:** `createEmployee` / `updateEmployee` call `parseEmployeeInput` (`empleados/schemas.ts`, `server-only`, `zod`), which replaced `validateRequiredFields`. It normalizes first (RFC/CURP uppercase without spaces; account without spaces or hyphens), then reuses `getStampingIssues` for formats, required fields and the contract/regime rule, and returns the first error as `{ ok: false, message }` naming the field. Nothing is written on failure. "La sucursal no tiene estado" is excluded here: it must not block saving.
- **`ClaveEntFed` is derived, not stored:** `dbo.sucursales.id_state` → `dbo.Cat_states.state_key` (already the SAT `c_Estado` key). `getEmployeeById` returns it as `clave_estado_sat` (`NULL` when the branch has no state, which counts as a missing item for fiscal employees). There is no per-employee state field.
- **Fiscal name is derived, not stored:** `nombre + apellido_paterno + apellido_materno` uppercased, shown read-only in the record. No `nombre_fiscal` column: if the PAC rejects the name, the employee's name is corrected.
- **UI:** `EmployeeModal.tsx` has the "Datos fiscales (CFDI de nómina)" section (RFC, CURP, NSS, CP, regime, contract, workday, union); account and bank stay in "Información laboral", the bank select is disabled and cleared when the account is a CLABE, and the asterisks follow `getRequiredStampingFields`. The record shows an `EmployeeFiscalStatusBadge` in the header (only for fiscal employees) and a "Datos fiscales" block in `EmployeeGeneralInfo.tsx` with catalog descriptions, the derived name, the `ClaveEntFed` and the list of pending items. All three are Server Components.
- **Known data caveat:** employees whose current data breaks a rule (bad RFC/CURP/account, or missing fiscal data) are shown as incomplete and **cannot be saved from the modal until corrected**.
- **Not implemented yet** (their own specs): CFDI de nómina stamping (XML/Facturapi payload, PAC, cancellation, receipts, payment dispersion); employer data (registro patronal, `RiesgoPuesto`, issuer RFC and Facturapi organization); SDI/SBC (IMSS); a `nombre_fiscal` field and accent/character normalization for the PAC; validating RFC, name and CP against the SAT; a completeness column or filter in the employee list; structured address and `SubContratacion`.
